== What is ros2_controller ? ==
Note that diff_drive is a controller, but it is limited in the system. When I will add motor to the legs, I will need
another controller to control them (something like joint-bending controller in ros2, it called joint_trajectory_controller).

ros2_controller is a framework which allows us to organize our project in a certain way so that the code written 
for the simulation will completly work the real world. Because it is well organize, it allows us to manage different
controllers in the project.

It is separate in 3 levels:
 ** Controllers ** : Intead of using gazebo controller (diff_drive), we will use ros2_diff_drive_controller to 
 do the work. I will allow ros2 to manage motor intead of gazebo and ros2 can manage multiple controller at the
 same time and check if their are working well. the controllers will be defined in a .yaml file.

 ** Controller Manager **: it takes the mathematical output from the controller and make sure that there is not 
 conflit between ctrls.

 ** Hardware Interface **: it translate number into electronic signal. It here we will specify the motors
 of our robot.  To communicate with gazebo to send cmd, we use the plugin 'gz_ros2_control'. The hardware Interface
 is written in an urdf file.

**** SLAM ****
SLAM: Simulation Localisation And Mapping
It is an algorithmique system approach used by the robot to map his environment and navigate.
It uses sensor fusion (Odometry, lidar, cameran IMU)
It is an algorithm which allows robot vacuums, self-driving cars and mars rovers to navigate unknow environments without GPS.


SLAM briefly, is when the robot know where it is and where the objects are.
This approach is not globally precise as a GPS but locally, it is.
Mapping: the map of the environment
Localization: location of the robot relative to the map.

SLAM maps grid approach
Odometry effectively measures robot velocity.
Among multiple navigation algorithms that exist, SLAM allows to correct drifting errors. By using the lidar and odometry, combined
with computer vision algorithms and optimization methods. So that we can more accurately estimate the robot pose and map.

******** Localization *********
What it is: Calculating your exact X, Y coordinates and orientation on a known map.
The Input: LiDAR laser scans + Odometry (wheel turns) + The pre-saved Map.
The Output: A single data point called a Pose (position and orientation).
The Tools: slam_toolbox (in localization mode) OR AMCL.
Note: It does 0 driving, it just generate the map.

mapping mode
→ Use when creating a new map.
The robot updates and expands the map while moving.
localization mode
→ Use when you already have a saved map.
The robot only localizes itself inside the map without modifying it.

Path A: Standard Nav2 Localization (AMCL)
This is the industry standard for autonomous navigation. It uses your .pgm and .yaml files.
It uses an algorithm called AMCL (Adaptive Monte Carlo Localization). When you launch it, it 
randomly scatters thousands of "guesses" (particles) across your map. As OTTO drives and its 
LiDAR pings the walls, the algorithm kills off the guesses that don't make sense, until all 
the particles cluster tightly around OTTO's true position.

Path B: SLAM Toolbox Native Localization
This uses your .data and .posegraph files.
Instead of running a separate AMCL node, you simply launch SLAM Toolbox again, but you change the mode: in your slam.yaml config from mapping to localization. SLAM Toolbox loads its mathematical 
memory, locks the map so it won't draw any new walls, and just matches your current LiDAR feed 
against its saved graph to figure out where you are.
